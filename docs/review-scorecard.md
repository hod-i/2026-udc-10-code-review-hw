# Рахунок рев'юера

> Task B і C. Правила підрахунку — з ключа відповідей (окреме репо, поза цим репо).
> Рев'юер: Claude Code + `/review N` ([`.claude/commands/review.md`](../.claude/commands/review.md)),
> модель Claude Opus 5.5. Кожен PR — окрема нова сесія. Вихід дослівно — `review-runs/pr-N.md`.

## Як рахував

- **Знайдено (TP)** — коментар рев'юера називає суть дефекту з ключа в правильному місці.
  Серйозність може не збігатися.
- **Пропущено (FN)** — дефект із ключа, якого не назвав жоден коментар.
- **Хибна тривога (FP)** — **блокуючий** коментар (у рев'юера — позначка «блокує») про те,
  що не є дефектом. Дрібниці й «Питання до автора» — нейтральні.
- **Дубль** — блокуючий коментар, що описує вже зарахований дефект з іншого боку (наприклад,
  слабкий тест, через який цей дефект пройшов). Не TP і не FP — нейтральний.
- Спірні коментарі, яких немає в ключі, я перевіряв за `PR.md` і `change.diff`. Якщо
  дефект не підтверджено вимогами PR — рахую як FP (консервативно, щоб не завищувати
  precision). Нижче окремо показано, як змінюються цифри, якщо їх рахувати нейтрально.

## Висновок

- **Що рев'юер робить добре.** В обох прогонах знайшов усі 15 дефектів, зокрема всі 5
  порушень домовленостей команди ([стандарт]). Стандарт із Task A працює: рев'юер прямо
  посилається на правила (журнал доступу, копійки, CHANGELOG). Не послухався
  коментаря-ін'єкції в PR-6 і назвав його. На PR-4 без дефектів жодного блокера.
- **Що дав Task C.** Хибні тривоги 3 → 0, дублі 4 → 0, точність серйозності 5/15 → 8/15, без
  втрати recall. Хибні тривоги були не «галюцинаціями», а надто буквальним застосуванням
  правил: їх прибрало явне розмежування «блокер з доказом» / «питання до автора».
- **Головний урок.** Правило проти хибних тривог саме спричинило пропуск (проміжний PR-3): «не
  блокуй без правила в стандарті» сховало справжній дефект. Будь-яке послаблення треба
  перевіряти регресійним прогоном на **всіх** PR, а не лише там, де були FP.
- **Де йому не можна довіряти.**
  - Серйозність: досі розходиться з ключем у 7 із 15 — пріоритет визначає людина.
  - Межа «знахідка / питання» залежить від формулювання одного правила: той самий дефект
    (екранування CSV у PR-3) в одному прогоні блокує, в іншому стає питанням. Серйозність
    теж «плаває» між прогонами на однаковому конфігу (повтор PR-2: журнал доступу critical ↔ high).
  - Тести рев'юер не запускав — висновки «тест пройде/впаде» він виводить з читання коду.
    Детерміновані перевірки (тести, CHANGELOG, grep на гроші й дати) мають бути в CI, а не
    на рев'юері.
  - 15/15 на шести PR — мала вибірка, і прогін 2 налаштовано під помилки прогону 1: на новій
    черзі recall і precision, найпевніше, будуть нижчі.
